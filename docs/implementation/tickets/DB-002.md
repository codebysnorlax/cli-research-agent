## Purpose
Create the job repository — the ONLY interface for creating, reading, and updating email jobs. This is the bounded API that prevents raw SQL from leaking into the application. All operations use parameterized queries.

## Current State
Schema exists (DB-001 complete). No repository code.

## Required Change
Create job repository with all operations documented in doc 06 §4:
1. `createJob(payload)` — insert new job, generate EMAIL-XXXXX ID
2. `getJob(id)` — fetch job by ID
3. `updateStatus(id, fromStatus, toStatus)` — atomic status transition
4. `claimJob(id)` — atomic SCHEDULED → PROCESSING
5. `listByStatus(status)` — list jobs in given status
6. `listScheduled()` — all SCHEDULED jobs
7. `listDue(now)` — SCHEDULED jobs where scheduled_at ≤ now
8. `cancelJob(id)` — SCHEDULED → CANCELLED
9. `rescheduleJob(id, newDatetime, timezone)` — update scheduled_at
10. `markSent(id, gmailMessageId)` — PROCESSING → SENT
11. `markFailed(id, error, isRetryable)` — PROCESSING → FAILED or schedule retry

// Atomic: SCHEDULED → CANCELLED
// Returns: boolean

// Returns: boolean

// Returns: boolean

// PROCESSING → FAILED + set last_error, increment attempt_count
// If isRetryable and attempts < max: PROCESSING → SCHEDULED (retry)
// Returns: { status, retryScheduled? }

export function getNextJobId(db)
// Returns: "EMAIL-XXXXX" (auto-incrementing, zero-padded)

## Data Changes
All operations modify `email_jobs` table. No schema changes.

## Behavior
- `createJob` generates sequential `EMAIL-XXXXX` IDs (query max existing, increment)
- All status updates use `WHERE status = ?` for atomicity
- `claimJob` sets `claimed_at` timestamp
- `markSent` sets `sent_at` and `gmail_message_id`
- `updated_at` is set on every mutation
- All timestamps stored as ISO 8601 UTC strings

## Security
- All queries use parameterized statements (no SQL injection)
- No raw SQL exported — only bounded functions

## Failure Cases
- `createJob` with missing required fields → throw validation error
- `updateStatus` with wrong fromStatus → returns false (0 rows affected)
- `claimJob` on already-claimed job → returns false
- `getJob` with non-existent ID → returns null
- `cancelJob` on non-SCHEDULED job → returns false

## Edge Cases
- Job ID wraps at EMAIL-99999 → document behavior (unlikely in POC)
- Empty listDue result when no jobs are due
- `rescheduleJob` on cancelled job → returns false (status mismatch)
